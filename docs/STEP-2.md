# STEP 2 — Product UX & Core Flows

## Status

**Step 2 is conceptually complete.**

This document records the decisions and UX flows discussed during Step 2. It translates the product principles from Step 1 into concrete user journeys without yet defining the technical implementation or database schema.

---

# 1. Core UX Principle

PathLevel follows:

> **Capture first, organize later.**

The user should be able to save information quickly without being forced to classify, summarize, or place it into a Learning structure immediately.

The product separates:

- **Capture** — save something before it is forgotten.
- **Review** — decide what the captured information is for.
- **Organization** — connect information to Learning when appropriate.
- **Learning** — actively study, reflect, and track progress.
- **Resurfacing** — bring old knowledge back when it becomes relevant.

---

# 2. Step 2A — Capture Flow

## Goal

Capture must be fast and minimally disruptive.

### Standard flow

```text
User discovers something
        ↓
+ Capture
        ↓
Input URL / file / text
        ↓
Save
        ↓
✓ Saved to Inbox
        ↓
User remains in previous context
```

The application should not automatically redirect the user to a detail page or force them to organize the item.

## Inbox meaning

Inbox means:

> **Information that has been captured but has not yet been fully reviewed/processed.**

It does NOT mean:

> Unfinished tasks.

Therefore:

```text
Inbox: 47
```

must not feel like 47 overdue Todo items.

## Capture metadata

A resource does not need complete metadata to be valid.

A user may know only:

```text
Title
URL
```

The system can attempt metadata enrichment later.

Potential metadata:

- title
- source/provider
- author
- description
- thumbnail
- publication date
- topics
- duration

If enrichment fails, the resource must still be saved successfully.

---

# 3. Step 2B — Review Flow

Review answers:

> **What should I do with this captured information?**

A captured item can generally be:

1. **Keep Saved**
2. **Add to Learning**
3. **Archive**
4. **Edit**

## Keep Saved

The item remains in the user's Library as useful knowledge without requiring a Learning relationship.

## Add to Learning

The resource is connected to an existing or new Learning Goal/Unit.

## Archive

The item is no longer currently useful but is not permanently deleted.

## Edit

The user can correct or complete metadata generated by the system.

---

## Batch / Quick Review

Inbox should support quick review because the number of captured items may become large.

Example:

```text
Docker Guide
[Keep] [Archive] [Learning]

PostgreSQL Article
[Keep] [Archive] [Learning]

AI Architecture
[Keep] [Archive] [Learning]
```

Full detail should be available when needed, but should not be required for every item.

---

# 4. AI During Review

AI is an assistive layer.

It may suggest:

```text
Suggested Learning:
Backend Development
→ Docker Fundamentals
```

The user must be able to:

- accept the suggestion
- choose another Learning
- reject it
- edit the relationship

AI must never silently determine the user's Learning structure.

## AI failure principle

```text
AI failure ≠ product failure
```

If metadata extraction or AI enrichment fails:

```text
Resource
↓
Still saved
↓
User can edit/review manually
```

Core capture functionality must not depend on AI.

---

# 5. Step 2C — Add to Learning Flow

## Fundamental principle

Adding a resource to Learning is a **relationship**, not a move or duplication.

The resource remains in the Library.

```text
Library Resource
       │
       └── Learning Relationship
```

Removing the Learning relationship must not delete the resource.

---

## Case A — Existing Goal + Unit

Fastest flow:

```text
Add to Learning
      ↓
Select Unit
      ↓
Add
```

If the system already knows the relevant Unit, it can provide a quick suggestion.

---

## Case B — Existing Goal, no appropriate Unit

```text
Add to Learning
      ↓
Select Goal
      ↓
+ Create New Unit
      ↓
Create & Add
```

Unit creation should happen inline rather than forcing the user to leave the current flow.

---

## Case C — No Learning Goal

The user can create one inline:

```text
Add to Learning
      ↓
Create Goal
      ↓
Create Unit (optional)
      ↓
Add Resource
```

---

## Case D — User does not know where the resource belongs

AI may suggest a Learning relationship.

Example:

```text
Docker Networking Guide

Suggested:
Backend Development
→ Docker Fundamentals

[Add]
[Choose another]
[Not relevant]
```

The user remains the final decision maker.

---

# 6. Goal-Level / Unassigned Resources

A resource may be connected directly to a Learning Goal without immediately being placed inside a Unit.

Example:

```text
Photography
│
├── Unassigned Resources
│   ├── Exposure Tutorial
│   └── Camera Basics
│
├── Exposure
│   └── Exposure Triangle Guide
│
└── Composition
    └── Rule of Thirds Article
```

This is intentional.

Users often know:

> "I want to learn X."

before they know:

> "What should the complete structure of X look like?"

Therefore:

> **Goal can exist without Units, and resources can remain unassigned within a Goal.**

This supports gradual organization.

---

# 7. Multiple Learning Relationships

A single resource may be relevant to multiple Learning contexts.

Example:

```text
PostgreSQL Indexing Guide
        │
        ├── Backend Development
        │   → Database
        │
        └── Data Engineering
            → Query Optimization
```

The resource is not duplicated.

The system stores multiple relationships.

---

# 8. Step 2D — Learning Flow

Learning is not designed as a traditional LMS/course player.

PathLevel does not require:

```text
Lesson → Video → Next → Quiz → Next
```

Instead:

```text
Learning Goal
      ↓
Learning Unit
      ↓
Resources / Notes
      ↓
Learning Session
      ↓
Optional Summary
      ↓
User decides completion
```

---

# 9. Learning Goal

A Learning Goal represents the user's intent to learn something.

Example:

```text
Backend Development
```

It can exist without:

- Resources
- Units
- Sessions

This is valid:

```text
Learning Goal
    ↓
No Unit yet
No Resource yet
```

The user can build the structure gradually.

---

# 10. Learning Unit

A Unit is a more specific part of a Learning Goal.

Example:

```text
Backend Development
├── HTTP
├── REST API
├── Authentication
├── PostgreSQL
└── Docker
```

The Unit acts as the central context for:

- related resources
- notes
- learning sessions
- summaries
- completion state

---

# 11. Learning Session

A Learning Session records a learning activity.

A session is **optional**.

The user may consume a resource without creating a session.

Example:

```text
Authentication
      ↓
JWT Guide
      ↓
Open
```

No session is required.

## Session use case

When the user wants to record deliberate study:

```text
Start Learning Session
        ↓
Learn
        ↓
Finish Session
```

A session can contain multiple resources.

Example:

```text
Learning Session
├── JWT Guide
├── OAuth Article
├── Personal Note
└── Duration
```

---

# 12. Retrospective Sessions

Users can log a session after the learning activity already happened.

Example:

```text
Log Learning Session

Date: Yesterday
Duration: 60 min

What did you learn?
...
```

This is necessary because PathLevel is not required to be open during every learning activity.

---

# 13. Learning Summary

After a session, PathLevel may ask:

> **What did you learn?**

The summary is explicitly **optional**.

The user may:

```text
Finish Session
      ↓
[Skip]
```

and the session is still valid.

Or:

```text
Finish Session
      ↓
Write Summary
      ↓
Save
```

The summary is intended as a reflection/recall mechanism, not an assignment.

PathLevel should not reject short summaries or require a minimum length.

---

# 14. Completion Rules

The system must not claim that the user has mastered something.

The user decides when a Unit is complete:

```text
[Mark as Complete]
```

Completion is a user-defined state, not an automatic mastery judgment.

A completed Unit can later be reopened.

Example:

```text
Authentication
✓ Completed Aug 5

New material found Aug 20
↓
Reopen
↓
Continue learning
```

Historical sessions and summaries remain.

---

# 15. Resource Progress vs Learning Progress

These are separate concepts.

Example:

```text
Course:
12 / 50 videos watched
```

does not automatically mean:

```text
Learning Unit:
24% complete
```

Likewise:

```text
Coursera:
42% provider progress
```

does not automatically become:

```text
PathLevel:
42% Learning progress
```

Provider progress and PathLevel Learning progress remain separate.

For V1, external provider progress should not require provider API integration.

---

# 16. Step 2E — Search & Resurfacing

Search and resurfacing are different mechanisms.

## Search

User explicitly asks:

> "Where is something I saved?"

```text
User Query
   ↓
Search
   ↓
Relevant Knowledge
```

## Resurfacing

PathLevel proactively shows previously saved knowledge because it may be relevant to the user's current context.

```text
Current Context
      ↓
Previously Saved Knowledge
      ↓
Potentially Relevant Item
```

---

# 17. Global Search

There should be one global search across the knowledge system.

Search should be able to find:

- Resources
- Notes
- Learning Goals
- Learning Units
- Learning Summaries
- potentially Sessions/activity records

Search should consider available textual content such as:

- title
- content
- summary
- topics
- personal context

Search results should preserve context.

Example:

```text
PostgreSQL Indexing Guide
Article · Saved Aug 8

Linked to:
Backend Development
→ Database
```

---

# 18. Search Technology Roadmap

V1 should not depend on RAG or vector search.

Recommended progression:

```text
V1
Full-text / keyword search

Later
Better filters
Relationship-aware search

Future
Semantic Search
Embeddings
RAG
Ask My Knowledge
```

The product must already provide useful search before AI is introduced.

---

# 19. Knowledge Resurfacing

Resurfacing should prioritize:

### Level 1 — Explicit relationships

```text
Current Unit
↓
Linked Resources
```

### Level 2 — Topic relationships

```text
Current topic
↓
Matching Library topics
```

### Level 3 — Semantic relationships

Future:

```text
Current context
↓
Semantic Retrieval
↓
Related knowledge
```

### Level 4 — Time-based resurfacing

Potentially show older knowledge when it is relevant.

It should not become a random old-bookmark feed.

---

# 20. Resurfacing Philosophy

Use:

> **Related from your Library**

rather than an engagement-oriented recommendation model.

Example:

```text
From Your Library

You saved these earlier.
They may help with Docker Fundamentals.

How Docker Actually Works
Docker Networking Guide
Docker Security Notes
```

Resurfacing should be:

- contextual
- sparse
- relevant
- actionable

It should not become an endless content feed.

---

# 21. Step 2F — Home / Dashboard Flow

Home is not an inventory of all features.

> **Home is a decision/context surface.**

It should answer:

1. What am I currently learning?
2. What saved knowledge may be relevant now?
3. What did I recently do?
4. What supporting activities matter today?

---

# 22. Home Hierarchy

Recommended hierarchy:

```text
Priority 1
Continue Learning / Current Focus

Priority 2
Relevant Knowledge / Resurfacing

Priority 3
Recent Learning Activity

Priority 4
Tasks / Habits

Priority 5
Achievements / XP
```

Not every section must always appear.

---

# 23. Continue Learning

If an active Learning Unit exists:

```text
Continue Learning

Docker Fundamentals
Backend Development

◐ In Progress

[Continue]
```

This should be the primary return action.

If there is no active Learning:

```text
No active learning

Explore your Library or start a Learning Goal.
```

The Home page must remain useful without Learning.

---

# 24. Tasks, Habits, XP, and Achievements

These remain supporting features.

They should not dominate Home.

Example:

```text
Today's Tasks
□ Update documentation
□ Submit assignment

Habits
✓ Study
✓ Exercise

Recent Achievement
7 Day Learning Streak
```

The application should not return to a "feature soup" dashboard.

---

# 25. Core Navigation Direction

Conceptually:

```text
Home

Library
├── All
├── Resources
├── Notes
├── Inbox
└── Archived

Learning
├── Goals
└── ...

Tasks

Habits

Achievements
```

Global actions:

```text
Search
+ Capture
```

Capture should be highly accessible because it is a primary product behavior.

---

# 26. Step 2G — Daily Return Loop

The goal is not maximum engagement.

The goal is **knowledge and learning continuity**.

Primary reasons to return:

1. Continue Learning
2. Review resurfaced knowledge
3. Capture something new
4. Supporting routines

---

# 27. Continue Learning as Primary Return Loop

Example:

```text
Yesterday
Authentication
45 min

Today
Continue Authentication
```

This is stronger than using a streak as the main motivation because it directly reinforces the product's core purpose.

---

# 28. Habit System

Habits remain useful as a behavioral support layer.

Example:

```text
Study
Read
Exercise
```

But application events should not automatically become habits.

Do not create habits such as:

```text
Open App
Search Library
View Achievement
Capture Item
```

unless the user explicitly wants those behaviors tracked.

---

# 29. Streak vs Learning Progress

These represent different things.

```text
Study Streak
= behavioral consistency

Learning Progress
= progress through a Learning structure
```

Example:

```text
Study Streak
12 days → 0

Docker Fundamentals
60% → remains 60%
```

Inactivity must not erase Learning progress.

---

# 30. XP and Achievements

XP is a reward layer.

It should reward meaningful activity rather than simple application usage.

Do not award XP merely for:

```text
Open app
Start session
Finish session repeatedly
```

The existing XP anti-abuse concerns should be handled separately in technical/domain rules.

Achievements represent milestones such as:

```text
First Learning Session
10 Learning Sessions
First Learning Goal Completed
100 Resources Saved
10 Learning Units Completed
```

They should not become daily obligations.

---

# 31. Notifications

Notifications should be contextual and useful.

Good examples:

```text
You were learning Authentication.
Continue where you left off.
```

```text
You saved this earlier.
It may be relevant to your current learning.
```

Avoid default engagement bait such as:

```text
Don't lose your streak!
Open PathLevel now!
You haven't opened PathLevel today!
```

The product should not punish inactivity.

# 32. Step 2H — Cross-Flow Review

The complete system was tested against representative scenarios.

## Scenario: User finds a YouTube course while busy

```text
YouTube
↓
Capture
↓
Save to Inbox
↓
Return to YouTube
```

Valid.

---

## Scenario: User knows only title + URL

```text
Title + URL
↓
Save
↓
Metadata enrichment if available
```

Valid.

Missing metadata must not block capture.

---

## Scenario: User has 50 captured items

Inbox requires quick/batch review.

Valid requirement:

```text
Keep
Archive
Learning
```

should be available without opening every item.

---

## Scenario: User has 500 Library items

Global search becomes critical.

Browsing and search serve different purposes:

- Search = find something known
- Library = browse/explore/review

---

## Scenario: External Coursera course

Represent it as an external resource.

For V1:

```text
Provider progress
≠
PathLevel Learning progress
```

Do not build provider synchronization unless there is a future product reason.

---

## Scenario: 50-part YouTube bootcamp

A course/playlist does not automatically become 50 Learning Units.

Resource progress can be:

```text
12 / 50 videos
```

while Learning Unit progress is independent.

---

## Scenario: One resource belongs to multiple Learning contexts

Supported through multiple relationships.

No resource duplication.

---

## Scenario: User has no idea what they want to learn

Do not automatically create Learning Goals.

AI may identify patterns and suggest a Goal, but the user decides.

---

## Scenario: User has a Goal but no structure

Use:

```text
Goal
├── Unassigned Resources
└── Units
```

The user can organize later.

---

## Scenario: User learns from multiple sources

One Learning Session may reference multiple resources.

```text
Session
├── YouTube
├── Documentation
├── Article
└── Note
```

---

## Scenario: User learns outside PathLevel

Allow retrospective Session logging.

PathLevel is not required to be open during every learning activity.

---

## Scenario: AI fails

The core product must continue working.

```text
AI unavailable
↓
Resource still saved
↓
Manual editing/review available
```

---

## Scenario: AI recommendation is wrong

The user can:

```text
Accept
Choose another
Reject
Edit
```

User authority remains above AI.

---

## Scenario: User never writes summaries

Valid.

Summary is optional and should not create negative feedback or penalties.

---

## Scenario: User becomes inactive

Learning state remains intact.

Behavioral metrics such as streak may change, but:

```text
Learning Progress
does not reset.
```

# 33. Step 2I — Learning Creation Flow

## Knowledge-first

```text
Resource
↓
Add to Learning
↓
Goal / Unit
```

## Goal-first

```text
Learning
↓
+ New Goal
↓
Goal
↓
Unit
↓

```

Both are valid.

# 34. Creating a Learning Goal

Keep the initial form minimal.

```text
Create Learning Goal

What do you want to learn?

[ Japanese ]

[Create Goal]
```

Do not force the user to define a complete curriculum.

---

# 35. Goal Without Unit

After creation:

```text
Japanese

You haven't added any learning units yet.

+ Add Learning Unit
```

This is valid.

The user can create structure later.

---

# 36. Creating a Unit

Minimal Unit creation:

```text
New Learning Unit

Name
[ Hiragana ]

Description (optional)
[ ... ]

[Create Unit]
```

Do not force the user to define:

- 10+ units
- prerequisites
- deadlines
- estimated hours
- complete curriculum

during initial creation.

---

# 37. AI Suggested Learning Structure

AI may help users who do not know how to structure a Goal.

Example:

```text
Machine Learning

Suggested Learning Structure

✓ Fundamentals
✓ Linear Regression
✓ Classification
✓ Model Evaluation
✓ Neural Networks

[Edit] [Create]
```

The user must review the suggestion before creation.

AI should provide a **suggested structure**, not claim to provide the one correct curriculum.

---

# 38. Existing Resources When Creating a Goal

If the user already has relevant resources:

```text
You have 18 saved resources
that may be related to Python.

[Review Resources]
```

The user selects which resources to connect.

Do not automatically reorganize all existing knowledge.

          │                   │

# 45. Step 2 — Final Decisions

### Capture

- Capture first, organize later.
- Capture must be fast.
- Save success must not depend on metadata enrichment.
- User remains in the previous context after global capture.
- Inbox represents captured-but-unreviewed information.

### Review

- Keep Saved.
- Add to Learning.
- Archive.
- Edit.
- Batch/quick review is required.
- AI suggestions are assistive only.

### Library / Relationships

- Resources remain in Library when connected to Learning.
- Relationships do not duplicate resources.
- One resource may connect to multiple Learning contexts.
- Goal-level / Unassigned Resources are supported.

### Learning

- Goal can exist without Units.
- Goal can exist without Resources.
- Unit is optional.
- Session is optional.
- Session can reference multiple resources.
- Sessions can be logged retrospectively.
- Summary is optional.
- User decides Unit completion.
- Completed Units can be reopened.
- Learning progress is separate from source/provider progress.

### Search / Resurfacing

- One global search across the knowledge system.
- V1 uses full-text/keyword search.
- Semantic search/RAG are future capabilities.
- Resurfacing is contextual, not a recommendation feed.
- Explicit relationships have the highest resurfacing priority.

### Home

- Home is a context/decision surface.
- Continue Learning has high priority.
- Relevant Library knowledge can surface.
- Recent activity is useful.
- Tasks/Habits remain supporting features.
- XP/Achievements should not dominate Home.
- Home remains useful without Learning.

### Daily Return

- Continue Learning is the primary return mechanism.
- Resurfacing is a secondary return mechanism.
- Capture is a natural return mechanism.
- Habits support consistency.
- Streaks do not affect Learning progress.
- Inactivity does not erase Learning progress.
- Notifications should be contextual, not engagement bait.
- AI-generated daily engagement content is not a priority.

### Learning Creation

- Goal-first and Knowledge-first flows are both supported.
- Goal creation is minimal.
- Unit creation is minimal.
- AI may suggest structure but must not silently create it.
- User can edit AI-generated suggestions.
- Existing Library resources can be connected to a new Goal/Unit.
- Capture from an active Learning context can use that context as an automatic relationship.
